# TG WS Proxy for iOS

[![iOS build](https://github.com/vibecoderqin/tg-ws-proxy-ios/actions/workflows/ios.yml/badge.svg?branch=main)](https://github.com/vibecoderqin/tg-ws-proxy-ios/actions/workflows/ios.yml)

A native SwiftUI iPhone/iPad app that embeds the Rust engine from
[`tg-ws-proxy-rs`](https://github.com/valnesfjord/tg-ws-proxy-rs) and exposes
its MTProto-over-WebSocket proxy controls in an iOS interface.

The Rust networking engine is kept as the protocol implementation. Swift is
the iOS host and UI; a small C ABI layer starts and stops the engine, forwards
logs, and returns the generated Telegram proxy link.

> [!WARNING]
> **This is currently a foreground prototype, not a reliable background proxy.**
> The listener runs inside the ordinary iOS app process. When you leave this
> app to open Telegram, iOS may suspend the process and stop the listener.
> Starting the proxy and opening its `tg://` link does not guarantee that the
> proxy will continue to work after the app goes into the background.

## Project status

| Component | Status |
| --- | --- |
| Upstream Rust proxy engine | Included and used by the iOS app |
| Rust-to-Swift C ABI | Implemented |
| Native SwiftUI controls | Implemented: start, stop, status, arguments and logs |
| Telegram proxy link | Generated by the Rust engine and shown in the app |
| Default listener | Loopback only: `127.0.0.1:1443` |
| Physical iOS device build | ARM64 build configured |
| GitHub Actions build | Rust tests, Rust iOS library, Xcode build and IPA checks |
| Signed distribution package | Not configured by default |
| Persistent background operation | Not implemented |
| Network Extension / VPN provider | Not implemented |

The current app is useful for developing and validating the iOS integration,
the Rust engine and the foreground UI. It should not yet be treated as a
finished solution for routing Telegram traffic continuously on the same
iPhone.

## How it is structured

```text
Telegram on the same iPhone
        |
        | MTProto via local proxy (127.0.0.1:1443)
        v
iOS app (SwiftUI)
        |
        | C ABI: start / stop / callbacks
        v
Rust FFI crate (crates/ios-ffi)
        |
        | Tokio runtime on a worker thread
        v
tg-ws-proxy-rs engine
        |
        | WebSocket/TLS and configured fallback transports
        v
Telegram data centres / configured upstreams
```

The iOS app does not reimplement the MTProto protocol in Swift. It calls the
existing Rust server implementation through `crates/ios-ffi`. The FFI layer
owns the Tokio runtime and provides callbacks for log messages, startup
information, errors and shutdown completion.

## iOS lifecycle limitation

An ordinary iOS application is not a general-purpose background daemon.
When the app becomes inactive or moves to the background, iOS controls whether
and how long it can continue executing. A normal background-task request only
provides limited additional time; it does not grant permanent execution.
Live Activities are presentation surfaces and do not keep the Rust listener
running.

For that reason, this project deliberately does **not** use continuous GPS
updates, silent audio playback, or other artificial keep-alive tricks.

A persistent networking design needs a separately designed and validated
Apple-supported architecture, the appropriate entitlements and (for some
Network Extension configurations) device management. A packet-tunnel provider
is not simply a way to keep a local TCP server alive. Review Apple's guidance
before changing the architecture:

- [Configuring background execution modes](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes)
- [Extending your app's background execution time](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)
- [NEPacketTunnelProvider](https://developer.apple.com/documentation/networkextension/nepackettunnelprovider)
- [Apple TN3120: Expected use cases for Network Extension packet tunnel providers](https://developer.apple.com/documentation/technotes/tn3120-expected-use-cases-for-network-extension-packet-tunnel-providers)

For dependable continuous proxy service today, the Rust engine is better
suited to an always-on external host (such as a server or router) than to a
normal foreground-only iOS app.

## Build

The iOS application is built on macOS with Xcode. The current Rust build script
targets **aarch64-apple-ios** (physical ARM64 devices); an iOS Simulator build
is not configured by this script.

### Requirements

- macOS with Xcode and the iOS SDK
- Rust toolchain with `rustup`
- XcodeGen
- The Rust target `aarch64-apple-ios` (added by `ios/build-rust.sh`)

### Build commands

Run from the repository root:

```sh
cargo test --locked -p tg-ws-proxy-rs
bash ios/build-rust.sh

brew install xcodegen
cd ios
xcodegen generate

xcodebuild \
  -project TgWsProxy.xcodeproj \
  -scheme TgWsProxy \
  -configuration Release \
  -sdk iphoneos \
  -destination 'generic/platform=iOS' \
  -derivedDataPath build \
  CODE_SIGNING_ALLOWED=NO \
  build
```

The Rust static library is written to `ios/Libs/libtg_ws_proxy_ios.a`.
XcodeGen creates `ios/TgWsProxy.xcodeproj`; the Xcode build output is under
`ios/build/`. Generated build products are not source files and should not be
committed.

### GitHub Actions

The workflow at
[`.github/workflows/ios.yml`](.github/workflows/ios.yml) runs on pushes to
`main` and can also be started manually. It:

1. Runs the upstream Rust engine tests.
2. Builds the Rust static library for iOS ARM64.
3. Generates the Xcode project.
4. Builds the iOS app without code signing.
5. Packages and validates the unsigned IPA.
6. Uploads the unsigned IPA as a workflow artifact when all validation steps
   pass.

Artifacts are retained for 14 days. A successful unsigned build is a build
result, **not** an install-ready signed app.

### Code signing

The repository does not contain Apple certificates, private keys or
provisioning profiles. The workflow can optionally perform a signed archive and
IPA export when the required private GitHub Actions secrets and configuration
are supplied. Without those credentials, it intentionally produces an
unsigned package only.

Do not commit `.p12` files, provisioning profiles, signing passwords, Apple
account credentials or private MTProto secrets to the repository.

## App behaviour

- The default command-line arguments bind the listener to
  `127.0.0.1` and advertise `127.0.0.1` in the generated link.
- The app displays the proxy lifecycle state: stopped, starting, running or
  stopping.
- Rust log messages are forwarded to the in-app log view.
- Proxy arguments can be edited in the app while the proxy is stopped.
- The generated `tg://proxy` link can be copied or opened from the app.
- The app displays a warning before opening Telegram because iOS may suspend
  the proxy process when the app leaves the foreground.

Keep the listener on loopback unless you have a specific, secured network
configuration. Do not expose a proxy listener to a Wi-Fi or public network by
changing the bind address casually.

## Contributing

When changing the iOS integration:

- Keep the Rust proxy engine as the source of protocol behaviour.
- Keep FFI callbacks safe to receive from background threads; update SwiftUI
  state on the main actor.
- Preserve loopback-only defaults.
- Do not claim persistent background operation unless it is implemented using
  an Apple-supported design and verified on a real device.
- Keep build output, signing material and secrets out of source control.
- Run the Rust tests and the iOS GitHub Actions workflow after changes.

See [`docs/IOS-PORT-REVIEW.md`](docs/IOS-PORT-REVIEW.md) for the review of the
separate Swift reference implementation and the architectural decisions made
for this port.
